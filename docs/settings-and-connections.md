# Settings and connections

Open Settings from the sidebar gear. Its six pages follow T3 Code's grouped settings and icon navigation. Project adds name/icon editing, manually launched local commands, and confirmed removal; see [Project settings](project-settings.md). The Update icon beside it checks stable Versionstead releases and shows release notes. No published release, a failed check, and a verified current build are distinct outcomes. Installer download/apply is not implemented for this source checkout.

The settings shell adapts T3 Code's compact Settings / Section breadcrumb and searchable sidebar. `/` focuses settings search and reveals a collapsed sidebar. Search covers available pages and ordinary setting rows; Arrow keys and Enter select a match, scroll to it, and focus it. Escape clears a search first, then returns to the last workspace page, preserving its filters. Back to workspace uses the same destination. Editing fields, selectors, and dialogs keep their keyboard behavior. The sidebar toggle remembers its visibility on this device.

Versionstead uses one integrated title bar. Windows retains native caption buttons with T3 Code's 40 px overlay and reserved control space; empty header areas drag the window and interactive controls remain clickable. Appearance mode also updates the native window theme. Normal window bounds and maximized state are saved in `window-settings.json` under Electron's user-data directory; saved bounds outside connected display work areas fall back to the default window. Browser headers use 52 px and remain ordinary page controls. Native macOS/Linux caption behavior still needs platform acceptance testing.

General's Restore device defaults asks for confirmation and resets appearance, keyboard shortcuts, and sidebar visibility on this device. It keeps custom themes, monitoring schedules, selected projects, accounts, and paired PCs. It does not reset the window's saved geometry.

## General, Appearance, and Keybindings

General controls scheduled scanning, PC/project intervals, automatic repository scans, summary notifications, and optional daily release checks. Pausing schedules leaves manual scans available. Background-host installation still uses the Windows setup script; a preference does not register a Windows task.

Appearance contains System/Light/Dark preview cards and the T3 Code, T3 Chat, Grove, Ocean, Ember, and Iris palette pairs. Select each light/dark orb independently or use a palette name for both halves. Create, duplicate, edit, import, or remove a custom theme; removing an active theme restores the default for that half. Theme JSON accepts Versionstead pairs and T3 Code's appearance/colors/variants format with literal hex or OKLCH colors, up to 64 KiB per file and 50 custom themes. Contrast, glass opacity, content width, panel animation duration, interface/monospace font families and sizes, word wrap, compact rows, and reduced motion apply immediately. Advanced typography adds table and evidence-panel font-size overrides. These controls are in Settings only; the sidebar footer has no Appearance switcher. Browser and Electron preferences remain separate. Keybindings supports capture, conflicts, disable, and reset; Reset all shortcuts asks for confirmation. Appearance and Keybindings need no coordinator connection, unlike the other settings pages. Defaults are Ctrl+, for settings, Ctrl+1–4 for workspace views, Ctrl+Shift+S for selected local-source scans, Ctrl+Shift+R for refresh, Ctrl+Shift+P for pause/resume, and / for page search. Command replaces Ctrl on macOS, where shortcuts read ⇧⌘S; the desktop's own platform decides, then the browser's. The capture dialog never traps focus: Tab, Shift+Tab, and Escape work as usual in it. Typing fields and dialogs retain their keyboard behavior.

## GitHub and GitLab

Source Control adapts T3 Code's actual discovery-row structure and VCS/provider SVG icons: compact grouped rows, inline CLI versions, status dots, switches, and expandable details. Repositories provides the automatic-scan switch and a scan-interval selector shared with General's project interval. A paused General schedule is explicitly shown here. Git's expander explains local branch/commit/working-tree context. GitHub/GitLab expanders contain connection actions, repository selection, selected refs/evidence status, and disconnect; the row switch opens connection setup for an unconnected account or pauses/resumes an existing connection. Opening setup alone does not authenticate or select anything. Account names use T3 Code's blurred placeholder and click-to-reveal behavior; the actual account text is absent from the concealed button. Refresh uses T3 Code's visibility-aware spinner, disables only that action while pending, and rechecks tools plus the protected provider credentials. Failed authentication retains previous evidence and reports an error; a later successful refresh clears it. Refresh does not select or scan repositories. Installed CLI, authenticated account, paused scanning, and connection error are distinct states; token connections also work without a CLI. Jujutsu, Azure DevOps, Bitbucket, and Forgejo/Gitea remain visibly Coming soon. Pull, merge, and generated change-request controls are outside Versionstead's current read-only scan workflow.

1. In Source Control, connect GitHub.com or GitLab.com. GitHub tokens need readable repository Contents/Metadata; GitLab tokens need `read_api`. Limit access to repositories you intend to monitor. Signed-in `gh`/`glab` token import is available in an interactive owner session.
2. Open Add Project from Projects and choose GitHub or GitLab. The searchable repository list loads automatically; select the ones you want, continue, and edit each branch/ref and maintenance intent on the confirmation screen. Git URL accepts HTTPS and `git@` SSH repository URLs on GitHub.com/GitLab.com and takes an accessible matching repository to confirmation. Local folder opens the existing native folder picker. Providers needing setup open Source Control. Its Select repositories action opens the same repository flow. Back and Escape return to the preceding step. Connecting an account selects and scans nothing by itself.
3. Confirm selection. With automatic repository scans and schedules enabled, scans start automatically and follow the project interval. Otherwise, scan manually from Projects.
4. Expand a project to inspect dependencies, coverage, ref, and scanned commit. Projects also provides maintenance/watch mode and removal.

Credentials use Windows DPAPI machine protection in the existing private SQLite database so the configured Windows background identity can unlock them. Protected connection credentials are currently Windows-only. Disconnect asks for confirmation, then forgets the current credential and retains evidence; revoke the token with the provider to fully end access, including old encrypted backups/journals.

Scans resolve one commit and read supported root npm/pnpm/Bun manifests and lockfiles plus workspace manifests identified by those lockfiles. Bun text lockfile v0/v1 scans include catalog ranges, aliases, nested resolutions, and transitive packages. Binary bun.lockb/newer formats remain unsupported. They never clone, restore, install, build, push, or run repository scripts. Missing/unsupported inputs and API failures remain explicit. Existing public npm/OSV privacy and coverage rules still apply. Private/custom registries, unsupported ecosystems, and self-hosted Git providers remain outside verified coverage. Discovery reads every page up to 10,000 repositories, then returns an explicit limit error; at most 50 projects can be selected overall.

Git discovery shows installed version and optionally records local branch, commit, and tracked working-tree status. It disables executable repository filters and fsmonitor and suppresses submodule checks. A status report larger than the output bound counts as dirty, and a failed inspection keeps the last recorded branch, commit, and status, with a coverage line saying that it could not be refreshed; turning Git context off clears them on the next scan. While Git context is off, Git is located but never run, so no version is shown. On macOS, Apple's `/usr/bin/git` stub is not run until `xcode-select -p` reports installed developer tools, so Git counts as not installed instead of opening the install dialog; the answer is kept until monitoring restarts. The Tailscale app bundle's command-line client is also a candidate on macOS. These macOS paths are covered by injected tests only; native macOS behavior is unverified. Jujutsu, Azure DevOps, Bitbucket, and Forgejo/Gitea are Coming soon.

## Pair PCs over LAN or Tailscale

Run Versionstead on both Windows PCs. Across networks, install and sign in to Tailscale on both; Versionstead does not administer your tailnet. Each PC keeps scanning its own selected sources with its own coordinator.

Connections follows T3 Code's machine heading, grouped rows, overflow menu, Environments list, empty state, and Add Environment mode cards. Local environment pauses/resumes scheduled scans on this PC; it leaves manual scans available. Version shows the actual loopback coordinator address and the checked release state. The machine menu refreshes connection/tool discovery, creates a pairing link, or configures network access. Refresh reads connection status and evidence without starting a scan.

Where the host has no protected credential storage (every platform but Windows for now), Network access, Tailscale HTTPS setup, and Add environment stay off beside the note "Protected connections require Windows."; Source Control shows the same note for its providers. Network access controls Versionstead's separate pinned HTTPS listener. Tailscale HTTPS offers the detected `100.x` address through the same setup dialog. This uses tailnet IPv4 and Versionstead's certificate pin; it does not configure Tailscale Serve, MagicDNS certificates, WSL, T3 Connect, or agent activity. Background monitoring describes the actual host mode and the remaining sign-out verification instead of offering those unrelated T3 agent controls.

For access after Windows sign-out or reboot, install the [Windows background host](windows-background.md) on each PC and enable **Preferences → Run unattended** from each Tailscale tray menu. Tailscale otherwise disconnects after sign-out on Windows. Verify both the background scan history and remote connectivity while signed out; see [Tailscale's unattended-mode guide](https://tailscale.com/docs/how-to/run-unattended).

1. On the PC whose evidence you want to read, open Connections and turn on Network access, or choose Set up beside Tailscale HTTPS. Select its LAN IPv4 or Tailscale `100.x` IPv4, choose an unused port (default 4389), and enable sharing.
2. Allow that inbound TCP port only from trusted LAN/tailnet peers in Windows Firewall. Versionstead does not create firewall rules automatically.
3. Choose Create pairing link from the machine menu or Authorized clients section and exchange it through a trusted channel. It carries an endpoint, device identity, certificate pin, and one-time code, expires in five minutes, and grants evidence-read and selected-source scan access. The dialog shows its expiry and supports copying, renewal, and separate host/code fields.
4. On the receiving PC, choose Add environment → Remote link and paste the full link into Host; the host and concealed pairing code fill automatically. Alternatively, enter the matching host and complete encoded invitation in Pairing code. Legacy encoded invitations also work. Add environment reports inline errors and closes after a successful connection.
5. The paired PC appears in Connections, the workspace sidebar, and Needs attention. Evidence refreshes every 30 seconds. Its switch pauses/resumes polling while retaining evidence and pairing. The row menu offers Refresh, Scan selected sources, and Remove; refresh/scan are disabled while the environment is paused. Remove asks for confirmation and attempts revocation. The environment name opens its retained evidence.
6. For access in both directions, repeat with the PCs reversed. Pairing grants no administrative settings, folder selection, arbitrary commands, or installation access.

The paired endpoint uses a Windows-generated self-signed certificate. Clients verify its pin before sending credential headers. The administrative coordinator stays loopback-only. Shared evidence omits local project/global-root paths, unsupported dependency requests that could contain credentials, and notification payloads.

Revoke a client on the host (after confirming) to block future reads/scans immediately. Remove attempts remote revocation; if the host is offline, revoke the client there when it returns. Disable sharing to stop listening while keeping pairing records. Offline evidence retains its last-received time and an explicit connection error.

Current limits: eight outgoing PCs, sixteen incoming clients, IPv4 literal endpoints, 4 KiB request bodies, 16 MiB received evidence, and one scan request per ten seconds per client. Certificates expire after one year; rotation/recovery UI remains future work. Central notifications for remote findings and physical LAN/Tailscale/firewall/sign-out validation remain open.

## Connect through SSH

SSH is an optional owner-session transport to an already-running Versionstead monitor. It forwards that monitor's pinned HTTPS endpoint rather than installing a backend or executing a remote command. For unattended access through a Windows boot host, use Remote link over LAN/Tailscale instead: the service does not access the owner's SSH profile, keys, or interactive agent.

1. Start Versionstead on the remote Windows PC, enable its peer endpoint, and create a pairing link as above. Configure an SSH server separately; Versionstead does not install or start it.
2. In the local owner's terminal, verify the SSH host key in `known_hosts` and set up key/agent authentication. Versionstead uses strict host-key checks and batch mode; it cannot display password or key-passphrase prompts. An already unlocked agent or an appropriate configured identity is required.
3. Choose Add environment → SSH. Search literal aliases from the monitoring owner's `.ssh/config` or enter a host. Select the username and SSH port (default 22). Simple `Host`, `HostName`, `User`, `Port`, `IdentityFile`, `UserKnownHostsFile`, and `HostKeyAlias` entries are supported. Keys/known-host files must be local absolute or `~/` paths. Include, Match, proxy, and executable directives are rejected; unsupported configuration requires a simple profile or Remote link.
4. Choose Add environment to continue to verification, then paste the remote monitor's pairing link. It supplies the peer endpoint, device identity, certificate pin, and one-time code independently of the SSH host. Complete pairing to save the environment.

The tunnel listens only on local loopback. SSH connects using the chosen host/user/port; its forward reaches the invitation's private IPv4 address and HTTPS port. Certificate/device checks still apply inside the tunnel before Versionstead sends credentials. A saved SSH environment reuses its live tunnel, retries a dead connection during normal evidence polling, and closes it on pause, removal, or coordinator shutdown. It retains evidence across outages and restarts just like a Remote link environment.

This differs from T3 Code's agent bootstrap because Versionstead scans only sources already selected on the remote monitor. Actual SSH server authentication and physical remote connectivity still require acceptance testing. See the official [OpenSSH client options](https://man.openbsd.org/ssh) and [SSH configuration](https://man.openbsd.org/ssh_config).

## Verification

`pnpm check` runs formatting, lint, types, builds, and regressions. `pnpm desktop:smoke` checks the native tray/window, real local scans, settings routes, shared appearance, Source Control expanders and connection setup, shared repository/project interval persistence, shortcut capture/conflicts and the confirmed reset, a failed Add project reported once inside its own dialog, schedule persistence, and update panel. Connections checks cover local pause/resume, Network access dialog selections in the native top layer, pairing-link autofill, concealed codes, Remote link/SSH mode switching, Escape/focus behavior, and narrow-window containment.

Provider regressions use controlled API responses for discovery, pagination, immutable file reads, selected-only scanning, encrypted persistence, and retained failures. Pairing checks exercise two actual HTTPS coordinators on isolated loopback ports, Windows certificate creation, pin verification before credential transmission, one-time pairing, remote scans, offline retention, reconnect, and revocation. Connections regressions additionally validate pairing URL/manual fields, SSH configuration/argument safety and pre-start cancellation, disabled-environment persistence, authenticated HTTP schemas, and actual pinned TLS through a controlled TCP forward with the original authority. Browser checks pair an isolated peer through the real dialog and verify pause/resume and row actions. Native captures are under `.versionstead/verification/connections/native`. These establish neither successful real SSH authentication nor physical second-PC connectivity.

For physical acceptance, pair two Windows PCs, verify the LAN/tailnet route and firewall rule, scan their selected sources, close both windows, reconnect after an outage, and revoke access. Verify the Windows boot task separately across sign-out/reboot before claiming unattended operation on either PC.
