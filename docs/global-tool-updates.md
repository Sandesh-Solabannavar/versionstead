# This PC package updates

This PC offers **Update now** beside verified stable public-registry updates in the Electron desktop app. Windows hardware ran real updates in a live smoke on October 3, before Wave 1 changed the Update now button and tool discovery, and again on October 11 (npm through Update now and Bun through Update all, one disposable package each). The update adapter has run real npm updates in a Linux container — `semver@7.0.0` to the current release in a disposable prefix, and a read-only prefix that reports it is not writable; the Electron runner and button off Windows, Bun updates off Windows, and all macOS and Linux hardware are unverified. The installation evidence drawer also shows the exact command and **Copy update command**. Closing the window keeps a manually launched update running in the tray; Quit UI stops its process tree. Browser clients and paired environments cannot launch package updates; a browser shows **Copy command** instead, which copies the generic `npm install --global <name>@<version>` or `bun add --global <name>@<version>` command (without the observed prefix) for the owner to run, beside a note that updates run in the Versionstead desktop app. While a PC scan runs or the last update check failed, that button is inactive with its reason, and the drawer shows no command. **Update now** asks first when a warning applies: the update adds an install script the installed version lacks, its new version is deprecated by its publisher, or the release is younger than the release cooldown (three days by default; Settings › General). The question lists the warnings and offers **Update anyway**; with none, the update starts at once. A release with no known date is not held back, and a cooldown of 0 turns the age check off. That question has been exercised with a stand-in bridge, not by a live update.

**Update all (N)** sits beside Scan now in the desktop's This PC header. It opens a confirmation listing every verified update with its version change and Major, Minor, or Patch badge, grouped as ready updates, releases with no known release time (listed separately and still ticked), releases younger than the release cooldown (left out unless ticked), and updates you snoozed or ignored (left out unless ticked, each with its rule). Each row also shows Update now's warnings: an added install script, a release younger than the cooldown, a deprecated candidate. The chosen packages run one at a time through the same runner as Update now: fresh ownership resolution, exact-version verification, and no other update while it runs. A failed package skips the rest of its global location and the others continue. Stop takes effect after the current package finishes and starts nothing after it; it does not cancel an install already running, including a package that is still being checked. Quit UI stops the running installer. One PC rescan follows the last package. A progress panel shows each package's state and ends with a summary of updated, failed, and not started packages. Every package is rechecked against the current PC evidence before any of them starts, so a confirmation that has gone stale is refused as a whole. Like Update now, Update all is inactive, with its reason, while a PC scan runs, the last update check failed, or another update is running, and Update now's buttons say Update all is running while it does. Update all's verification is narrow: the live smoke runs one Bun package through it on Windows (its npm fixture goes through Update now), the order of several packages, the skip after a failure, Stop, and quitting are covered only by tests with stand-in installers, and macOS and Linux are unverified.

The control uses the compact outline button, download/spinner icons, per-installation pending state, failure/retry feedback, fresh ownership resolution, installer locking, and post-command verification. Only npm/Bun global inventory is updated; native, Homebrew, and pnpm updaters are not used.

## Discovery and ownership

Explicit absolute local PATH directories retain their order. On Windows, discovery appends these common CLI directories when absent:

- `%APPDATA%\npm`
- `%LOCALAPPDATA%\Programs\nodejs`, `%LOCALAPPDATA%\Volta\bin`, `%LOCALAPPDATA%\pnpm`
- `%USERPROFILE%\.local\bin`, `%USERPROFILE%\.bun\bin`, `%USERPROFILE%\scoop\shims`

Configured `BUN_INSTALL\bin`, `VOLTA_HOME\bin`, `PNPM_HOME`, and `ProgramFiles\nodejs` are also fallbacks. Relative paths, network shares, duplicates, shell-profile execution, and current-directory executable resolution are excluded. The same fallback list locates desktop Node and the managers used to capture global sources.

On macOS and Linux the same list follows PATH with the usual install and version-manager locations, because an app launched from the Finder or Dock inherits only `/usr/bin:/bin:/usr/sbin:/sbin`:

- macOS: `/opt/homebrew/bin`, `/usr/local/bin`, `$BUN_INSTALL/bin` or `~/.bun/bin`, `$VOLTA_HOME/bin` or `~/.volta/bin`, `$PNPM_HOME` or `~/Library/pnpm`, `~/.local/bin`, `~/.local/share/mise/shims`, `~/.asdf/shims`, `/usr/bin`, `/bin`
- Linux: `/usr/local/bin`, the same Bun and Volta directories, `$PNPM_HOME` or `~/.local/share/pnpm`, `~/.local/bin`, `~/.local/share/mise/shims`, `~/.asdf/shims`, `/usr/bin`, `/bin`, `/snap/bin`

POSIX executables run under the name they were found by and are never resolved first, because Volta, mise, and snap shims are multi-call binaries that dispatch on their own name. A Node other than the running coordinator is verified by a bounded probe that reports its `process.versions.node` and real `process.execPath`. That reported path, whatever the candidate is called, starts the coordinator or runs npm's script, which is looked for beside the launcher and beside that Node. Local project `outdated` checks (see [Package-manager checks](package-manager-checks.md)) ask a Bun candidate the same way, from an empty private directory, and run only the executable it reports inside a project, because mise, asdf, and Volta shims read the project directory and may install what it pins. PC discovery asks a Bun candidate the same way, except a mise shim, which is never run because mise installs a tool declared `lazy = true` the first time its shim runs: a Bun found only that way is reported as unavailable, and the desktop looks for its Node among mise's installed versions instead. These probes, scans, and tool discovery also switch mise's auto-install off; [Package-manager checks](package-manager-checks.md) describes what that leaves. Absolute directories only, no shell, and no current-directory resolution are unchanged. These locations have platform-injected tests; native macOS and Linux behavior remains unverified.

This discovers the active npm and Bun executables and their configured global roots; it does not recursively inventory every old Node installation or every directory in the list. Ownership comes from the active executable rather than updating every installation. Versionstead already has package/root identities from installed manifests. npm's actual JS CLI is validated and invoked through absolute Node; Windows batch shims are not executed. Bun's supported configuration/environment precedence still determines its root. A successful owner-session discovery is required immediately before updating, including when monitoring uses a LocalService boot host.

## Manual execution

Trusted Electron main-frame IPC accepts only a collected installation ID, expected installed version, and selected stable target version. Main rechecks the current authenticated coordinator snapshot. The focused adapter rediscovers the manager and verifies its root, installed manifest, canonical package name, alias, version, and public origin. Changed, private, linked, unsupported, prerelease, unavailable, or stale targets are rejected. PC scans must finish before a new update starts.

npm installs the exact selected package version with an explicit observed global prefix. Bun requires the exact global manifest and its direct dependency declaration, then adds the exact selected version with `BUN_INSTALL_GLOBAL_DIR` fixed to the observed directory and that directory as its working directory. A missing manifest is rejected before execution, preventing Bun's ancestor-manifest fallback. npm aliases remain aliases. Bun's copied command includes its global-directory assignment as well. Updates preserve each manager's normal lifecycle-script/trusted-dependency settings; npm 12 receives the target package's script approval. These are explicit software installation actions, separate from read-only scanning.

The desktop permits one update per global root, so two packages cannot concurrently mutate the same installer state. It uses argument arrays, absolute executables, no shell, a five-minute deadline, a one-MiB output limit, and process-tree cancellation. Inherited Node/Electron execution overrides are removed. Raw output is discarded; status and permission failures are sanitized, transient, and not stored in SQLite or shared with peers. Versionstead does not elevate updates; unwritable prefixes require the owner's authorized terminal.

Exit zero alone does not establish success. The adapter rereads the original package/root identity and requires the selected version. Every terminal outcome requests a PC rescan, including failure because a partially completed install can change files. Results survive route changes while Electron remains running. Background scheduling never initiates an update; signed-out monitoring retains read-only access.

The package manager runs with the environment discovery used: mise's auto-install switches off and `BUN_OPTIONS` cleared. `bun add --global` reads the owner's global `~/.bunfig.toml` (or `$XDG_CONFIG_HOME/.bunfig.toml`), as the owner's own command would. The `bun -e` identity probe does not: Bun 1.4 reads the global file only for package-manager commands ([command_tag.rs](https://github.com/oven-sh/bun/blob/bun-v1.4.0/src/options_types/command_tag.rs#L93-L110)), and the probe's empty private directory holds no `bunfig.toml`, so neither applies a `preload`.

## Verification

Run `pnpm check` and `pnpm desktop:smoke`. The optional live Windows smoke installs only `semver@7.0.0` into two disposable global roots, clicks the actual npm **Update now** button and the Bun **Update all** button (its confirmation must list exactly that one package, ticked), verifies the selected newer stable release and refreshed evidence, rejects stale requests, and removes its isolated state. Both Bun's exact global manifest and a separate parent guard manifest are initialized before installing the fixture; the parent must remain unchanged throughout setup and updates. It requires installed npm and Bun plus public-registry connectivity:

```powershell
$env:VERSIONSTEAD_SMOKE_VERIFY_GLOBAL_UPDATES = '1'
pnpm desktop:smoke
Remove-Item Env:VERSIONSTEAD_SMOKE_VERIFY_GLOBAL_UPDATES
```

The normal smoke never upgrades the owner's packages: when verified updates exist it opens Update all on the owner's real tools and declines it, checking that nothing starts, and when none exists (or the last PC scan failed) it says so instead. With the live fixtures it updates npm through Update now and Bun through Update all. Physical sign-out/boot and protected/system prefixes remain separate acceptance tasks. Automated checks cover aliases, PATH fallbacks, changed roots/versions, private sources, escaping symlinks, exact verification, duplicate starts, retry, cancellation, sanitized failures, and process bounds.

The Linux container check runs `VERSIONSTEAD_LIVE_GLOBAL_UPDATE=1 node --test --test-name-pattern=live: apps/server/test/global-tool-updates.test.mjs` as a non-root user; it contacts the public npm registry.
